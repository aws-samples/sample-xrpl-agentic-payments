Reference Architecture — Agentic AI Cross-Border Payments

Multi-agent autonomous payment system built on Amazon Bedrock AgentCore and the XRP Ledger. AI agents handle compliance, routing, execution, and settlement — end-to-end in under 10 seconds. Five specialized agents, each constructed with its own scoped tool list, are invoked in a fixed sequence by a deterministic Python orchestrator running inside the web application — there is no LLM supervisor.

Target Operators: Financial institutions, payment providers, and licensed fintechs transacting on Ripple's XRP Ledger — deploying and operating AI payment agents in their own AWS infrastructure with full custody control.

1/5Components and the numbered request path

Where every component runs, which side of the AWS account boundary it is on, and in what order the hops happen — steps 0-11, plus the two targets T1-T2 that are designed but not built.
Browser → ALB → web app on EKS Graviton → orchestrator and its 5 agents in that same pod → AgentCore Gateway → Lambda tools → XRPL testnet. Moving the agent tier onto AgentCore Runtime (T1) and signing in KMS (T2) are drawn dashed because they are targets, not deployed.

2/5One payment, stage by stage

What actually happens between a person typing an instruction and the ledger having settled it — 12 stages, and the two places the run stops without a payment.
Both halts end the run before the Execution agent is constructed, so nothing in the process is holding submit_payment: a sanctions result other than CLEAR (stage 3), and an amount at or over $10,000 (stage 6).

3/5Inside the agent tier

The 5 agents, the fixed order they run in, and the exact tools=[...] list each one is allowed to call — which is what the authorisation boundary is made of today.
Sequenced by a deterministic Python function, not an LLM supervisor. Agent 3 (Routing) has no path to the Gateway at all, which is why only four of the five agents reach it.

4/5Why there are six wallets

Six XRPL accounts for five agents, plus a seventh for testing. What each one is for, and — honestly — which of them the running system actually uses.
RLUSD has to be issued by someone, so one account is the issuer; the account that signs payments is deliberately not that issuer; and one account per agent gives each agent its own on-ledger identity. Today that per-agent split is an attribution boundary, not a custody boundary — all seeds live in one Secrets Manager secret and signing is local.

5/5The x402 exchange, message by message

What is actually on the wire between a buyer agent and a merchant agent, in order — 16 messages, and which one of them moves money.
The buyer signs but never submits — the merchant's facilitator submits, so what crosses the wire is an authorisation, not funds. /verify touches no ledger and is free to repeat; /settle is the only message that moves money, and it is sent after the work is done. Step 8 is the one implementations leave out: the buyer echoes back the terms it chose, so the merchant must compare that echo against its own published price before trusting anything.

Stages 3 and 6 are the two halts, and both are evaluated in plain Python against the request the server validated at stage 2 — never against the amount or destination the model restated back. Either one ends the run before the Execution agent is constructed. The approval hold is an awaiting_approval status in this application, not a Step Functions human-approval workflow, and signing at stage 8 happens in application memory: KMS-backed signing is target T2 on slide 1.

AWS Services Used

Compute: Amazon EKS (Graviton3 c7g) + Karpenter
AI/ML: Amazon Bedrock (Claude Sonnet 4.5, Guardrails)
Tool path: Bedrock AgentCore Gateway (MCP, 8 Lambda targets, x402) — the agents themselves run in the EKS pod; AgentCore Runtime is target T1
Signing: local (xrpl-py, seed in memory) — AWS KMS ECC_SECG_P256K1 is target T2, not built
Auth: AWS IAM / SigV4 (AgentCore Gateway)
Tool Scoping: Per-agent tool lists in application code (Cedar policies: target, not built)
Secrets: AWS Secrets Manager — wallet seeds read by the Lambda tools at invoke time, never mounted into the web pod (the Secrets Store CSI driver mounts only the web login secret)
Governance: awaiting_approval status in the application — Step Functions HITL is a target, not built
Audit: CloudTrail management events (no Trail provisioned by infra/, so tool invocations are not captured yet)
Observability: Container Insights + X-Ray + ADOT
Networking: ALB + Route 53 + VPC (private subnets)
Settlement: XRP Ledger (RLUSD, native DEX, escrow)
Payments: AgentCore Payments (x402, Coinbase CDP)
